# Shared Backup Bot — public controller

This repository contains generic backup code and synthetic tests only. Do not upload application code, configuration JSON, database dumps, backup assets or credentials here.

Daily backups and manual runs execute only on the approved commit of protected `main`, with Environment Secrets restricted to that branch. Lock `main` including administrators after reviewing the installed code. Set the repository variable `BACKUP_APPROVED_SHA` to the full reviewed commit SHA. Updating code requires explicit review, unlocking/relocking main and approving the new SHA. No second account or daily reviewer is required for an owner-operated frozen installation. This is owner review, not independent two-person approval.

The workflow has two fixed profiles. `brote` retains the `backup-production` and `backup-monitor` environments. `violeta` uses `backup-violeta-production` and `backup-violeta-monitor`; both jobs stay disabled unless the repository variable `BACKUP_VIOLETA_ENABLED` is exactly `true`. Each profile has fixed job-to-Environment bindings, distinct concurrency groups and release prefixes. Dispatch accepts only the declared profile choices; runtime rejects a mismatched profile identifier. There is one backup engine, not one installation per profile.

Create each profile's Environments with Selected branches and tags: exactly branch `main`, no tags. Put `BACKUP_CONFIG` and its credentials only in the matching Environment; use a different vault token, encryption password, Supabase credentials and project CA certificate (`BACKUP_PG_CA_PEM`) for every profile. Fine-grained vault tokens must be restricted to that profile's private vault. The supplied CA is validated and mounted read-only for psycopg, the independent Storage inventory connection and pg_dump; TLS remains `verify-full`. Never use repository-level production secrets or paste configuration into Issues, workflow inputs, Variables, source code or PRs. `violeta` configuration must contain `"profile_id": "violeta"`; the old Brote configuration without that field is accepted as `brote` for transition compatibility. Every additional profile needs a reviewed allowlist and fixed Environment-bound jobs.

Scheduled times are independent: Brote backup/monitor at 02:17/06:47 UTC; Violeta at 03:17/07:47 UTC, gated by `BACKUP_VIOLETA_ENABLED`. GitHub cron is best-effort, not an exact-time guarantee. Do not set the Violeta enable variable until its Environment, tokens, private vault, recovery design and synthetic isolation checks have been reviewed and authorized.

Actions exposes execution dates, workflow stages and success/failure publicly. Detailed status, backup/restore dates, object counts and notifications live exclusively in the private vault. The public summary contains no private links, hashes, names, counts or database contents. No backup artifacts are uploaded to public Actions. Exceptions from production tools are suppressed.

The manual operations are `daily`, `restore-latest` and `pre-migration`. The last operation consumes an immutable, hash-pinned private rehearsal specification; it executes the approved SQL only inside a disposable networkless PostgreSQL container. There is no remote migration or remote restore command.

GitHub Free supports protection and Environment Secrets for public repositories. A private repository using unrestricted repository Secrets does not provide the same boundary. This controller does not change visibility of any existing repository and requires no paid integration.

A monthly workflow without Environments or private secrets writes only the public month to `automation-heartbeat`, keeping activity off the locked code branch. Its temporary GITHUB_TOKEN can write this public repository; branch protection must include administrators, disable bypass, force pushes and deletion. It never writes main. Public scheduled workflows can be disabled after 60 days of inactivity; check Actions if the heartbeat fails. GitHub cron and provider outages have no guaranteed delivery. Private vault PATs require renewal; no system on these constraints can honestly promise zero maintenance forever.

Backup retention: 14 daily, 8 weekly, 6 monthly, pre-migration 30 days, `[KEEP]` releases indefinitely, independently applied to each profile's private vault. Only encrypted assets go to private Releases. Releases are not WORM/PITR or a separate provider. Preserve each encryption password offline. PostgreSQL restore and Storage-byte hash verification do not prove a full managed-Supabase recovery: importing Storage bytes, restoring Auth identities in a new project, and recovering OAuth/SMTP/JWT/Edge Functions/domains still require separately tested, authorized procedures.

The shared controller remains a concentrated code/configuration risk. Separate Environments do not prove absolute isolation: wrong Environment setup or an over-scoped PAT could cross the intended boundary. Review job/profile bindings and verify negative cross-profile tests before enabling any new profile.
